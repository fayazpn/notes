- JS engine has 3 main parts
    - Thread of execution
    - Memory/Variable environment
    - Call stack
- Browser parts
    - Web browser API/Node Background API
    - Promises
    - Event Loop, Callback/Task Queue and micro task queue
    - console, timer, DOM - document, network requests, timer - setTimeout, sockets, XHR - fetch, localStorage, indexDB etc
- When browser functions are executed they are not run in execution context, it is run in web browser features
- Web browser features has two parts, complete ? and onCompletion
- Callback queue, the ‘callback’ is not run inside the browser function, it just places the function back into the call stack from the queue
- sync code is always having the priority
- When the call stack is empty is only when the callback queue will be dequeued and placed into the call stack
- All regular code (global code) should be run before anything is run from the queue
- Checking if call stack empty and if something is there the callback queue is called ‘event loop’
- Callback hell, when async function gets data, it can only access the data inside the callback function that is given inside the browser function operating inside the data creates something called callback hell
- We don't have access because we don't run the function explicitly by ourselves, browser does for us
- All the browser features until now, has no way of giving its progress to the JS engine
